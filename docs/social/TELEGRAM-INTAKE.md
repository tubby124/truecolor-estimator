# Photo intake and exact review

Implementation dated September 7, 2026. This page describes the new feature; it does not certify production activation. The current-state board records release status. Core draft, media, preview, approval and scheduling state belongs to the application. Telegram is an optional Hermes transport; future website clients can reuse the service behind staff authentication. Commercial billing and other-business onboarding are not implemented. The current generation voice is True Color only.

## Owner workflow

Drop a photo, optionally captioned with factual context, in the configured True Color Telegram topic. The existing Hermes bot creates one durable intake and two drafts. An open Regina date at 10 a.m. is proposed, with no automatic replacement of existing posts. Open the temporary HTML link to review Instagram and Facebook separately, then approve the exact image, both captions, date and image rights using the bound button. The two drafts become ready and enrolled in the existing scheduler atomically. The queue and calendar read those same posts. Successful-post Telegram messages continue through the existing monitor.

Change date or caption using the preview controls and an exact reply. Dates such as `date 2026-09-15 10:00` are interpreted in Regina. A taken date returns alternatives. Revised versions invalidate old approval controls. An approved but unattempted pair can be revised, withdrawing approval/enrollment; attempted or posted images cannot be reset through this flow. Direct content edits through legacy staff pages deliberately invalidate the intake snapshot and require reconciliation; use the Telegram controls for these packages.

Original and prepared photographs stay in the private `social-originals` bucket. Read-only expiring HTML uses short-lived signed image access and contains no scripts, site trackers or approval endpoint. During an explicit approval, the server promotes only the exact reviewed SHA256 bytes to the existing publishing bucket, rechecks canonical media/facts/destinations and atomically approves both posts. Viewing or forwarding a preview is never approval. Links are read capabilities: anyone given a valid link may see its current preview until expiry. Changes invalidate the old link.

Basic preparation corrects orientation, keeps the complete photograph, pads if necessary and creates a publishable JPEG. Optional cleanup/background removal runs a separate bounded image worker; it does not use EDA's publishing queue. New edited bytes create a fresh review version. Human review remains necessary for lettering, logos, colours and edges. Image-generation failure never falls back to a paid image API or approves the original automatically.

## Activation package

1. Review and obtain production SQL approval for `supabase/migrations/20260907180000_social_photo_intake.sql`. It adds three RLS-protected service-only tables, transactional intake/revision/approval functions and a private storage bucket. It does not modify historical post content or publish anything. Apply in one transaction with lock/statement timeouts, then verify tables/functions/bucket privacy and preserve existing approved-post snapshots.
2. Set distinct strong `SOCIAL_INTAKE_SECRET`, `SOCIAL_INTAKE_APPROVAL_SECRET`, and `SOCIAL_INTAKE_PREVIEW_SECRET` in protected app configuration. Set verified `SOCIAL_INTAKE_BUSINESS_ID`, `SOCIAL_INTAKE_OPERATOR_ID`, and `SOCIAL_INTAKE_ENABLED=true`. Existing business membership is still checked. The draft credential cannot call approve; the preview token cannot mutate anything.
3. Install the reviewed `scripts/social/hermes-plugin` package in the existing default gateway's user plugin directory. Follow its README: pin actual bot/owner/chat/topic IDs, use protected distinct secret files, enable only this plugin, and perform one coordinated gateway restart. Do not launch another poller, bot or webhook. Preserve unrelated Hermes configuration and dirty ops work.
4. Enable `SOCIAL_INTAKE_SCHEDULER_ENABLED=true` and set `includeIntake:true` in the existing VPS ongoing configuration. Install the matching scheduler/monitor scripts. This is a deliberate configuration-fingerprint change: pause the sole timer, back up journals, reconcile the old exact queue, then preserve its phase and update the fingerprint/heartbeat. Keep the existing base IDs. Do not delete monitor outbox/initialization markers or replay old receipts.
5. Active enrolled versions extend the exact base queue only when both app and runner opt in. Edited/withdrawn approvals are excluded; historical posted enrollments do not fill active-queue capacity. Receipt history is independently paginated, and the monitor retains a two-day overlap while holding its watermark during pending provider outcomes. Maximum active intake scope is 400 destinations; exceeding it requires operator attention rather than truncating work.
6. Image enhancement requires the separate worker readiness and synthetic canary described in `scripts/social/enhancement/README.md`. No image API, social provider credentials or EDA media are passed into its creative process. Its managed Codex session receipt must prove completed built-in image-generation bytes match the output. Only configure enhancement controls after verification.
7. Run one real owner photo through intake, both previews, revision, explicit owner approval, scheduled delivery and independent public receipt readback. A code release, synthetic fixture or private preview alone does not prove that end-to-end delivery.

## Recovery and limits

Requests bind a stable Telegram message-derived UUID to bytes/context. Repeating it cannot create another pair. A genuinely uncertain generation/save retains a held request instead of spending again. `/social retry` recovers an already-saved result after a lost response; a held preparation needs operator inspection of its retained original/generation job. Do not manufacture new request IDs to bypass that state.

Approval is an idempotent database operation, not provider dispatch. A new explicit owner click may retry after fresh identical review readback; simultaneous clicks cannot approve twice. Provider dispatch still uses the existing durable CAS and uncertainty protection. Cleanup jobs retain attempt/result checkpoints and do not automatically regenerate after ambiguity.

The optional Telegram adapter has no LLM tool registration and reads its approval credential only for a verified callback. The default Hermes gateway still has its existing privileged shell capabilities; this is application-level credential separation, not a claim that the root-running gateway is OS-isolated from its own configuration.

Turning intake flags off disables new requests and intake scheduling. Preserve existing pending/provider receipts and journals. Do not disable the original base queue or change already-approved September content during rollback. Originals and job records are retained; no automatic deletion policy is introduced.
